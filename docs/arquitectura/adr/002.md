# ADR 002: Elección de Kong API Gateway como Puerta de Enlace de la Arquitectura

- **Estado:** Aprobado
- **Fecha:** 2026-10-17
- **Autores:** Equipo de Arquitectura y DevSecOps

## Contexto
La adopción del patrón **Strangler Fig** implica que el monolito heredado y los nuevos microservicios deben coexistir en producción durante todo el proceso de migración. Para evitar que los clientes conozcan la topología interna o tengan que gestionar múltiples puntos de acceso, se requiere una capa de intercepción centralizada. Esta pieza debe ser capaz de enrutar el tráfico de forma dinámica y transparente hacia el sistema antiguo o hacia los nuevos servicios, al tiempo que unifica la seguridad y la observabilidad sin obligar a modificar el código legado.

## Decisión
Seleccionar **Kong API Gateway** como puerta de enlace estándar de la plataforma para habilitar la transición gradual:
- **Enrutamiento dinámico y convivencia:** Redirigir peticiones por rutas (*path-based routing*) o cabeceras entre el monolito y los microservicios, facilitando migraciones progresivas (*Canary releases*) y reversiones (*rollbacks*) instantáneas si un servicio nuevo falla.
- **Desacoplamiento de la seguridad:** Centralizar la autenticación y autorización en la capa de borde mediante plugins (OAuth2, OpenID Connect y JWT), liberando a los nuevos microservicios y al monolito de gestionar estas validaciones de forma aislada.
- **Gobierno y protección del tráfico:** Aplicar políticas uniformes de *Rate Limiting*, *Throttling*, CORS y auditoría centralizada antes de que las solicitudes lleguen a los servicios internos.

## Consecuencias
### Positivas
- **Migración transparente para el consumidor:** Los clientes interactúan con una única fachada unificada mientras la arquitectura interna evoluciona pieza por pieza.
- **Alto rendimiento y baja latencia:** Capacidad probada para gestionar altos volúmenes de tráfico gracias a su núcleo basado en NGINX / OpenResty.
- **Ecosistema extensible:** Amplio catálogo de plugins listos para usar en seguridad, transformación de tráfico y observabilidad.
- **Preparado para Cloud-Native:** Integración nativa con flujos modernos y orquestadores como Kubernetes / K3s.

### Desafíos
- **Curva de aprendizaje operativa:** Requiere capacitar al equipo en la administración declarativa de rutas y políticas mediante `decK` y archivos YAML bajo un enfoque GitOps.
- **Criticidad en la infraestructura:** Al actuar como punto único de entrada (*Single Point of Entry*), exige desplegarse en alta disponibilidad para evitar que se convierta en un cuello de botella.
